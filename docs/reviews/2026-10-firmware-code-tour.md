# Fix the failsafe before the RideOnESP32 drives

The RideOnESP32 project is a small, flat Arduino codebase: two competing single-file sketches (`sketch_jun22b.ino`, v2.1, and `sketch_jun22b_OOP.ino`, v2.2), one `platformio.ini`, a dozen Markdown docs and three PDFs, all built around an ESP32 that drives four BTS7960 H-bridges from an ExpressLRS/CRSF receiver or a pedal and shifter. The safety layer looks thorough on paper but would not protect a child in practice. **The v2.1 sketch does not compile. Every radio channel is read off by one. The radio failsafe cannot detect a lost link.** The thermal input watches for a BTS7960 pin that does not exist, the current-sense scaling is roughly 100 times wrong, and no fault ever drops the hardware enable line. Neither sketch builds under the PlatformIO layout as committed, and several docs describe hardware and code that no longer exist. The OOP sketch is the better base, because it compiles and its signed ramping removes instant direction reversals. The owner's first job is a short list of safety fixes on that base: gate driving on `crsf.isLinkUp()`, fix the channel indices, make GPIO21 a real kill switch with latched faults and a throttle-zero arming check, and treat bad voltage and current readings as faults. Build cleanup and doc rewrites come after that.

## Two sketches, one motor class and a superloop

Both sketches have the same shape: pin `#define`s and compile-time tunables, global state, `setup()`, and a `loop()` paced by `delay(10)`. There are no FreeRTOS tasks, interrupts, watchdog, Wi-Fi, Bluetooth or persistent configuration ([sketch_jun22b.ino](../../archive/v2.1/sketch_jun22b.ino)). Each loop iteration calls `crsf.update()`, reads telemetry, reads six CRSF channels, refreshes a radio-alive timestamp, picks MANUAL or REMOTE mode from a radio channel, reads the shifter, runs `checkSafetyConditions()`, then either stops the motors or runs the remote or manual logic. It ramps PWM every 20 ms and prints telemetry once a second (sketch_jun22b.ino:586-653). Only three subsystems actually work. **CRSF input** comes in on UART2 (RX16/TX17, 420000 baud) through the AlfredoCRSF library. **Manual input** is a pedal pot on GPIO34 and shifter switches on GPIO39 and GPIO5. **Motor output** is one shared speed and direction sent to all four BTS7960s (FL 25/26, FR 27/14, RL 12/13, RR 32/33), with a common enable on GPIO21. Steering, horn and sound pins are declared and partly initialised, but nothing uses them: `steeringInput` and `hornInput` are read and then ignored (sketch_jun22b.ino:178-191, 549-570, 599-600).

The v2.2 OOP sketch is a partial refactor. Its one class, `BTS7960Motor`, holds per-bridge pins, a **signed** speed from −255 to +255, an enable flag, ramping and current reading. Four global instances replace the duplicated `ledcWrite` blocks ([sketch_jun22b_OOP.ino:89-331, 430-433](../../archive/v2.2/sketch_jun22b_OOP.ino)). Safety, telemetry and input handling are still global functions, and fan-out helpers still send every wheel the same speed. Per-wheel control is possible in the class but unused. Most of the size difference (859 vs 1286 lines) comes from deleted comments. The logic that was lost is about 60–80 lines: the 21 V and 35 A warnings, the current-imbalance check, the `TEMP_FAULT_INDIVIDUAL` option and the steering pin setup. OOP adds one real improvement and one regression. The improvement is that a DRIVE-to-REVERSE change now ramps through zero instead of swapping from full RPWM to full LPWM within 20 ms, as v2.1 does (sketch_jun22b.ino:1130-1132, 1205-1234). The regression is that current is read only in REMOTE mode but summed in every mode. In MANUAL mode `motorCurrent` therefore freezes at the last REMOTE value, and if that value was over 40 A the car stays disabled (sketch_jun22b_OOP.ino:634-641).

The compile break in v2.1 is concrete. `setup()` calls `pinMode()` on `RL_R_IS`, `RL_L_IS`, `RR_R_IS` and `RR_L_IS`, but those `#define`s are commented out (sketch_jun22b.ino:148-155, 523-526). A stubbed syntax check reports "not declared in this scope" for all four, while OOP passes cleanly. That alone shows v2.1 was never flashed in its current form. It also means the [OOP_REFACTORING_GUIDE](../../archive/docs-v2/OOP_REFACTORING_GUIDE.md) is wrong when it claims "v2.1 Compile ✅ Success", "All functionality identical" and "Production Ready".

## The radio path fails in two independent ways

The most dangerous defect is the radio failsafe, and it is broken twice over. First, AlfredoCRSF channels are **1-based**: `getChannel(ch)` returns `_channels[ch - 1]` ([AlfredoCRSF.h](https://github.com/AlfredoSystems/AlfredoCRSF/blob/main/src/AlfredoCRSF.h)). Both sketches pass `THROTTLE_CH = 0`, which reads `_channels[-1]`, an out-of-bounds access into whatever flag bytes precede the array. Every other function is shifted one channel too: the "mode switch" constant 3 reads transmitter channel 3, which on a standard AETR mix is the throttle stick, not a switch (sketch_jun22b.ino:197-208, 598-603). Because "throttle" reads as a small integer outside 900–2100, `lastRadioSignal` never refreshes after boot. Once the car is in REMOTE it fails safe after one second and never drives by radio. In this case the bug fails safe, by accident.

Second, and worse, fixing the indices alone makes the car unsafe. Liveness is judged only by the throttle value sitting between 900 and 2100 (sketch_jun22b.ino:607-609). AlfredoCRSF writes `_channels[]` only when an RC packet arrives, and on link loss it clears only `_linkIsUp` after 300 ms. The stale channel values stay ([AlfredoCRSF.cpp](https://github.com/AlfredoSystems/AlfredoCRSF/blob/main/src/AlfredoCRSF.cpp)). **After a real link loss the frozen throttle stays "valid" and the car keeps driving at its last command.** The fix is to gate on `crsf.isLinkUp()` or on packet age. Two related problems remain. The control mode itself comes from a radio channel, so a glitch reading below 1500 drops the car into pedal control (sketch_jun22b.ino:612). And the failsafe is evaluated only in REMOTE mode.

The superloop adds latency on top of this. Once a second, telemetry String concatenation pushes about 250 characters through 115200-baud Serial. That stalls the loop for about 20 ms, and at high ELRS packet rates it can overflow the 256-byte Serial2 RX buffer. This is an estimate from the code, not a measurement.

## Every protection layer either fails open or re-arms itself

The other safety features all fail in the same way. **Faults auto-clear with no latch, hysteresis or re-arm check.** As soon as all checks pass, `checkSafetyConditions()` sets `motorsEnabled = true`. That even overrides a PWM-attach failure flagged in `setup()` (sketch_jun22b.ino:486-498, 889-892). An over-current trip zeroes PWM, current then reads near zero, and the motors re-enable on the next loop. Low-voltage cutoff at 19.0 V has no hysteresis, so battery sag cycles the motors. Nothing requires the throttle or pedal to return to zero first, so a cleared fault can **surge the car forward** at whatever input is held, at boot, after a mode change or after failsafe recovery.

**The hardware enable is never used as a kill switch.** GPIO21 goes HIGH once in setup, before the eight PWM pins are attached and zeroed, and is never written again. `emergencyStop()` only writes PWM 0 (sketch_jun22b.ino:471-501, 1249-1266). Infineon's datasheet says INH must go low to turn both switches off. It also says an overtemperature shutdown stays **latched** until INH is pulsed low ([Infineon BTS7960 datasheet](https://www.phippselectronics.com/wp-content/uploads/2025/05/BTS-7960.pdf)). The firmware's "automatic recovery after 30 s" therefore cannot clear a real thermal latch. If the owner wired EN to VCC, which [BTS7960_WIRING_GUIDE](../../archive/docs-v2/BTS7960_WIRING_GUIDE.md) allows, the car has no hardware kill path at all.

**Thermal protection is a no-op.** The docs and both sketches expect an active-LOW "FAULT" output from each BTS7960, diode-OR'd onto GPIO19 ([THERMAL_MONITORING_OPTIONS.md](../../archive/docs-v2/THERMAL_MONITORING_OPTIONS.md)). The datasheet pin list is GND, IN, INH, OUT, SR, IS and VS. There is no FAULT pin. Faults are signalled by the IS pin sourcing 4–7 mA, which pulls it **high** ([Infineon BTS7960 datasheet](https://www.phippselectronics.com/wp-content/uploads/2025/05/BTS-7960.pdf)). Both the polarity and the pin are wrong. Even taken on its own terms, the 30 s recovery timer counts from fault onset, so a fault lasting longer than 30 s clears the moment it ends (sketch_jun22b.ino:800-816).

**Current sensing is wrong by about two orders of magnitude and partly absent.** The code assumes 1 mV/A. The BTS7960 sense ratio is about 8500, which gives about 118 mV/A across a 1 kΩ IS resistor ([Arduino forum, quoting the datasheet](https://forum.arduino.cc/t/bts7960-current-sensing-how-to-use-it/973355)). At the code's scale, ADC noise or a real 1 A reads as tens or hundreds of amps, so the 40 A over-current trip fires spuriously in REMOTE mode and the >100 A warning floods the log. RL and RR current are hard-coded to zero and the total is estimated as `(FL+FR)×2`. In MANUAL mode, the mode a child drives in, v2.1 forces `motorCurrent = 0`, so **over-current protection is completely absent there** (sketch_jun22b.ino:736-759). The 40 A limit also sits above the documented 30 A breaker ([Component_Descriptions_and_Purpose.pdf](../../archive/hardware_reference/Component_Descriptions_and_Purpose.pdf)), so the breaker would trip first anyway.

**Low-voltage cutoff fails open.** Readings outside 15–30 V are set to 0.0, and the cutoff only runs when `batteryVoltage > 0` (sketch_jun22b.ino:696-700, 830). A broken divider, an open wire or a pack sagging below 15 V all count as "OK". The 100k/12k divider also puts about 2.57–2.89 V on GPIO35, above the ESP32 ADC's accurate range of 150–2450 mV ([ESP32 datasheet](https://documentation.espressif.com/esp32_datasheet_en.pdf)). Readings near the 19/21 V thresholds are probably off by about 1 V. A freshly charged 24 V lead-acid pack, at about 27 V, also sits at the BTS7960's 27.5 V operating limit and 27.6–30 V overvoltage lockout ([Infineon BTS7960 datasheet](https://www.phippselectronics.com/wp-content/uploads/2025/05/BTS-7960.pdf)).

**Pin choices create electrical hazards that software cannot fix.** GPIO34 is wired as both the pedal and FR_R_IS, GPIO39 as both shifter-D and FL_R_IS, and GPIO35 as both battery voltage and FR_L_IS. The code only switches which software reading it trusts by mode, and two sources cannot share one physical node ([GPIO_PIN_ALLOCATION.md](../../archive/docs-v2/GPIO_PIN_ALLOCATION.md)). GPIO34–39 "do not have software-enabled pullup or pulldown functions" ([ESP-IDF GPIO docs](https://docs.espressif.com/projects/esp-idf/en/stable/esp32/api-reference/peripherals/gpio.html)), so `INPUT_PULLUP` on the GPIO39 Drive switch does nothing, and the input floats without an external resistor. GPIO12 (RL_RPWM) is a strapping pin. If it is held high at reset, flash voltage drops to 1.8 V and boot can fail ([esptool boot-mode docs](https://docs.espressif.com/projects/esptool/en/latest/esp32/advanced-topics/boot-mode-selection.html)). Finally, at load currents above about 28 A, or in the 4–7 mA fault state, a 1 kΩ IS resistor would put more than 3.3 V on an ESP32 input, beyond the 3.6 V rating ([ESP32 datasheet](https://documentation.espressif.com/esp32_datasheet_en.pdf)). Each IS line needs a divider or clamp.

## Neither sketch builds as laid out, and half the docs are stale

`platformio.ini` targets `esp32dev` with the Arduino framework. It overrides the framework with arduino-esp32 git tag 3.0.0 and pulls AlfredoCRSF unpinned from git, plus Adafruit MCP23017 and BusIO ([platformio.ini](../../archive/v2.2/platformio.ini)). It sets no `src_dir`, and PlatformIO defaults to `src/` ([PlatformIO docs](https://docs.platformio.org/en/latest/projectconf/sections/platformio/options/directory/src_dir.html)). That folder does not exist. Moving both `.ino` files into `src/` would also fail, because two `setup()`/`loop()` pairs in one firmware cause duplicate-definition errors. A concatenation test produced 52 errors ([PlatformIO community](https://community.platformio.org/t/can-a-single-platformio-ini-have-more-than-one-entry-point/37956)). The Arduino IDE would refuse the folder too, because the sketch file must match the folder name ([Arduino sketch specification](https://arduino.github.io/arduino-cli/1.5/sketch-specification/)). Both sketches need the core-3.x `ledcAttach`/`ledcWrite` API, and official PlatformIO "doesn't support Arduino Core 3.x" ([PlatformIO community](https://community.platformio.org/t/esp32-arduino-core-3-x-and-platformio-status/42008)). The dependable route is a pioarduino platform release in place of the raw git override ([platform-espressif32-versions](https://github.com/sivar2311/platform-espressif32-versions)). The MCP23017 dependencies are dead in v2.1 and serve only an `#ifdef` stub in OOP. `projects/myrient_autosearch.py` is an unrelated ROM-download script that was misfiled here.

The docs fall into two generations. The current set, which matches the code's pins, CRSF at 420000 baud, the 9.333 divider and the 19 V/40 A thresholds, is [BTS7960_WIRING_GUIDE](../../archive/docs-v2/BTS7960_WIRING_GUIDE.md), [HARDWARE_UPDATES_v2.1](../../archive/docs-v2/HARDWARE_UPDATES_v2.1.md), [QUICK_START_GUIDE](../../archive/docs-v2/QUICK_START_GUIDE.md), [GPIO_PIN_ALLOCATION](../../archive/docs-v2/GPIO_PIN_ALLOCATION.md), THERMAL_MONITORING_OPTIONS and USER_MANUAL. The [README](../../archive/docs-v2/README.md) is half updated: its parts list is current, but its pin table uses the old PWM/DIR names, and its divider (82k/12k) and thresholds (10.5 V, 15 A, ACS712) are 12 V-era values. [WIRING_GUIDE](../../archive/docs-v2/WIRING_GUIDE.md) is entirely 12 V-era. [BTS7960_TELEMETRY_GUIDE](../../archive/docs-v2/BTS7960_TELEMETRY_GUIDE.md) and TELEMETRY_UPDATE_SUMMARY describe eight current channels on pins the code had to abandon. [CHANGELOG](../../archive/docs-v2/CHANGELOG.md) stops at v2.0 and has no entry for v2.1 or v2.2. The hardware PDFs split the same way. The component PDF matches the 24 V architecture: battery, 30 A breaker, XH-M609 cutoff, two LM2596 bucks, four BTS7960s and four 200 W motors. The ELRS guide uses SBUS and even suggests flashing ExpressLRS onto the controller, which would erase the vehicle firmware ([ESP32_ELRS_Receiver_Connection_Guide.pdf](../../archive/hardware_reference/ESP32_ELRS_Receiver_Connection_Guide.pdf)). "Untitled Document.pdf" is a wkhtmltopdf render of USER_MANUAL.md. USER_MANUAL.md itself is about 93% leading-space padding, which makes it 649 KB and probably makes it render as one code block. Two documented wiring choices also need checking against the real car: feeding 3.3 V into "ESP32 VIN", and running BTS7960 logic at 3.3 V. The repo has no schematic or photo, so the as-built wiring is unknown.

## What to tackle first

The order below puts safety ahead of build hygiene, and it assumes the owner adopts the OOP sketch as the base. OOP compiles and already fixes reversal at speed. Its lost warnings can be ported back from v2.1.

| # | Fix | Why it comes here |
|---|---|---|
| 1 | Bench-test with wheels off the ground, and keep the kids off the car until items 2–5 are done | The current code can keep driving after radio loss and can surge when a fault clears |
| 2 | Change channel constants to 1-based (throttle = 1, and so on) and gate liveness on `crsf.isLinkUp()` or packet age, never on the channel value | The failsafe cannot detect link loss, and correct indexing alone makes that worse |
| 3 | Make GPIO21 the kill switch: hold it LOW at boot until PWM is zeroed, drop it in `emergencyStop()` and on every fault, and pulse it low to clear a driver latch. Confirm EN is not tied to VCC | Software PWM 0 is the only stop today, and thermal latches never clear |
| 4 | Latch faults, add hysteresis, and require throttle and pedal at zero before arming, re-arming or changing mode. Stop re-enabling after a setup failure | Faults currently auto-re-arm and can surge the car |
| 5 | Treat out-of-range voltage as a fault (below 15 V means cut off; near 0 V means sensor fault). Warn above about 27 V. Use `analogReadMilliVolts()` or a larger divider | Low-voltage protection currently fails open |
| 6 | Make current sensing real: scale for about 8500:1, clamp or divide each IS line, filter, treat IS saturation as a driver fault, keep it active in MANUAL mode, fix OOP's stale-current regression, and set the limit below the 30 A breaker | Current sensing is about 100 times off, absent in MANUAL, and can over-voltage the ESP32 pins |
| 7 | Replace the thermal design: read the IS-high fault flag, or add heatsink NTC/DS18B20 sensors, and drop the nonexistent FAULT pin | Thermal protection is currently a no-op |
| 8 | Rewire the shared pins (34/35/39) to separate inputs or an external ADC, add an external pull-up on GPIO39, and move RL_RPWM off GPIO12 | Two sources on one pin cannot work electrically, and the Drive input floats |
| 9 | Add a task watchdog, log `esp_reset_reason()` at boot, take the mode from a radio switch with a safe default, limit reverse speed, and move PWM to about 20 kHz | Covers resets, brownouts and remaining driver stress |
| 10 | Fix the build: create `src/main.cpp` from OOP, archive v2.1 outside `src/`, switch to a pioarduino platform, and pin the AlfredoCRSF commit | Needed for reproducible flashing |
| 11 | Rewrite or archive the stale docs (README, WIRING_GUIDE, telemetry guides, ELRS PDF), add CHANGELOG entries for 2.1 and 2.2, strip the padding from USER_MANUAL, and move the stray Python script out | Prevents wiring from wrong instructions |

Some of this remains uncertain. No real ESP32 build or bench run was done. The compile break and channel bugs come from source reading and a stubbed syntax check. The on-board IS resistor on the owner's IBT-2 modules, the transmitter's channel mix, and the actual EN and IS wiring are all unknown. The AlfredoCRSF behaviour was checked against current `main`, which an unpinned build would fetch, but older revisions were not checked.

## Conclusion

The striking pattern is that this codebase's documentation, its comments and its "tested" claims were written from intent, not from running hardware. The placeholder "Author: [Your Name]" header and the uncompilable v2.1 point the same way. The safety features exist as names and thresholds, but each one is wired to a signal that cannot carry the information it needs: a radio value that never goes stale, a fault pin that does not exist, a current scale that is off by 100 times, and an enable line nobody ever drops. Because of that, the right mindset is not "polish a working controller". It is "commission a new one": verify each safety signal on the bench against a deliberately induced fault (unplug the receiver, hold the pedal while a fault clears, short the divider) before trusting it.

A side benefit is that the OOP class already gives the structure needed for the deeper fixes. A per-motor enable, signed ramping and a place for per-bridge current calibration are all there. Promoting safety, radio input and manual input into similar small classes would make each fix above testable in isolation, which matters more on a vehicle a child rides than any feature on the docs' roadmap.
